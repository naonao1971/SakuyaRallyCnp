# 咲耶Nounラリー — SakuyaNounRally ⌐◨-◨ (proto)

旧称は「咲耶ラリーCNP / NOUN RALLY」。`localStorage` のキー
（`nounrally_best` / `nounrally_mute`）は**変えていない**。変えると
プレイヤーのベストスコアと音設定が黙って消えるため、表記だけを改めている。

CNP11体を集める Rally-X 系の迷路ゲーム。車は止まらず、曲がる方向だけを決めて
迷路を走り回り、散らばった11体を全部回収するとクリア。

`index.html` を開くだけで動く。ビルド不要、依存ライブラリなし。

姉妹作の [咲耶スクランブル](https://github.com/naonao1971/SakuyaScramble)
（横スクロールSTG、[sakuya.naoblock.jp](https://sakuya.naoblock.jp/)）とは
別ゲームだが、**登場する11体はキャラ・名前・絵ともに同じもの**を使っている。

> CNP（CryptoNinja Partners）の非公式ファンアート作品です。公式とは関係ありません。

## 遊び方

- 車は止まらない。**曲がる方向だけ決める**
- 迷路に散らばった CNP 11体を全部回収すると**出口が開く**。出口へ戻ればクリア
- **通った場所にタイヤ痕が残り、1マスにつき加点**される。同じマスは二度加点しない
- 画面上段に**11体のロスター**が並ぶ。取った枠は絵が起き、まだの枠はシルエット
- 赤い敵車に触れるとクラッシュ。**車は3台**あり、ぶつけても続きから走れる
- クラッシュしても CNP・スコア・迷路は引き継ぐ。自機と敵の配置だけ戻り、**復活後2秒は無敵**
- `SMOKE` で敵をスピンさせられるが、燃料を多く食う
- 燃料が尽きても即死しない。**減速する**（自機 2.625 → 1.75）ので敵に抜かれ、いずれ捕まる

| 操作 | PC | スマホ |
| --- | --- | --- |
| 曲がる | 矢印 / WASD | 画面を押したまま倒す（バーチャルスティック） |
| 煙 | Space | SMOKE ボタン |
| 音の入切 | M | 🔊 ボタン |

スコアの内訳。

| | 得点 |
| --- | --- |
| CNP n体目の回収 | `100 + n*20` 点（11体で合計 2420 点） |
| タイヤ痕 1マス | `PAINT_PTS` = 5 点（通路は約446マス＝最大 2230 点） |
| 出口へ到達 | `GOAL_BONUS` = 800 点 |

**CNPとゴールは全員同じ点なので、クリアした人どうしの差は塗りだけでつく。**
以前は全クリアすると誰でも必ず 2420 点で同着だった。ベストスコアは
`localStorage` に残る。

## `localStorage` を素のまま呼ばないこと（STARTが効かなくなる）

**`localStorage` は「あるのに触ると落ちる」ことがある。** 別オリジンの iframe で
動かしたとき（アーティファクト等）、iOS Safari の「サイト越えトラッキングを防ぐ」
（既定でオン）が効いていると、**`getItem` を呼んだ瞬間に `SecurityError`** が飛ぶ。

初期化の途中でこれを踏むとスクリプトがその行で死に、**以降の
`addEventListener` が1つも走らない**。HTML と CSS は生きているので画面は
いつも通りに見え、**STARTを押しても何も起きない板**になる。原因がどこにも
出ないので、見つけるのに時間がかかる。実際に踏んだ。

必ずこのラッパー越しに使うこと。

```js
const store = {
  get(k){ try{ return localStorage.getItem(k); }catch(e){ return null; } },
  set(k,v){ try{ localStorage.setItem(k,v); }catch(e){} },
};
```

再現の仕方（Playwright）:

```js
await ctx.addInitScript(()=>{
  Object.defineProperty(window,'localStorage',{configurable:true,
    get(){ throw new DOMException('The operation is insecure.','SecurityError'); }});
});
```

`sessionStorage` / `indexedDB` も同じ。**ブラウザの機能を初期化の本流で
素のまま呼ばないこと。**

## 向きの監視は「すべての宣言が終わってから」始めること

`updateOrientation()` は `state` と `bgmOn` を触る。この関数は画面の向きを扱う
都合でファイルの先頭近くに置いてあるが、**先頭で呼んではいけない**。
`state`（宣言は 300行目あたり）も `bgmOn`（700行目あたり）も `let` なので、
そこに届く前に読むと **TDZ で `ReferenceError`** になり、**スクリプトがそこで死ぬ**。

死んだ先が「STARTを押しても何も起きない板」なので、原因がまるで見えない。
**実際に踏んだ。**

**横で開くと踏まない。** `if(should===orientationBlocked) return;` があり、横持ちでは
`should` も `orientationBlocked` も `false` なので早期 return して `state` に届かない。
**縦で開いた実機だけが死ぬ。** 手元のテストは横から始めていたので、ずっと気づけなかった。

- 監視の開始（リスナー登録・`setInterval`・最初の1回）は **IIFE の末尾**で行う
- 念のため `var booted` で守る。`var` は巻き上げで `undefined` になるので、
  最初期に読んでも TDZ にならない（`let` にすると同じ罠に戻る）

### 画面まわりのテストは必ず「縦で開いて横にする」を通すこと

実機の流れは **縦で開く → 警告を見る → 横にする → START**。横から始めるテストでは
この経路が一度も通らない。`rotate.mjs` に入れてある。

| | 縦→横 | 横だけ |
| --- | --- | --- |
| 直す前 | **START が効かない** | 動く |
| 直した後 | 動く | 動く |

## 初期化で落ちたら画面に出すこと

上の件は「黙って死ぬ」のが一番たちが悪かった。本体より**前**に
`error` / `unhandledrejection` を拾う小さなスクリプトを置き、
`#crash` の帯にメッセージを出している。押すと消える。

本体より前に登録すること ― 本体の中で登録しても、本体が死ぬ側なので間に合わない。

**出すのは「最初のエラー」にすること。** 2件目以降は1件目で死んだ巻き添えで、
原因から遠ざかる。実際、真因は `bgmOn` の TDZ なのに、あとから 250ms ごとに出る
`state` の TDZ で上書きされ、そちらを追いかけた。いまは1件目を保持し、
`(以後 N件)` と件数だけ添える。

**出どころも必ず一緒に出すこと。** `window` の `error` は、このページのエラーだけ
でなく**拡張機能やコンテンツブロッカーが注入したスクリプト**のエラーも拾う。
ブラウザは別オリジンのエラーの詳細を伏せるので、`message` が
**`Script error.`、`filename` が空、`lineno` が 0** で通知してくる。

**このページは外部のスクリプトを一切読んでいない**（画像もアイコンも同一オリジン、
`<script>` は2つともインライン）。だから**ファイル名の無い `Script error.` は必ず
このページの外から来ている。** 実機で実際にこれが出て、ゲームが壊れたように見えた。

いまは `e.filename` も受け取り、ファイル名が無い `Script error.` には
**`［このページ外］`** と付ける。出どころを書かずに出していたせいで、無関係の
エラーでゲームが壊れて見えていた。

## 出口はスタート地点に置かないこと

11体そろえたあと**わざとクラッシュすれば復活位置＝出口**になり、残機1つで
ゴールを買えてしまう。`farthestCell()` でスタートから幅優先探索して最も遠い
通路マスに置いている。連結性は岩の判定（後述）で保証してあるので必ず到達できる。

11体そろっても**即クリアにしない**。`exitOpen` が立つだけで、そこから出口へ
戻るまでが一走り。戻る道中も塗れるので、最後に得点を伸ばす余地が残る。

## 操作はバーチャルスティック

スマホでは**画面のどこでも触れた場所にスティックが出る浮動式**。押したまま倒すと
その方向へ、離すと操作終了。十字パッドは廃した（150px を場所代に取られるため）。

### 出力は `heldDir` に入れること

スティックは「押している間ずっと続く**状態**」の入力なので、`heldDir` に流し込めば
十字キーを押しっぱなしにしているのと同じ経路を通り、`update()` が毎フレーム予約を
補充する。`WANT_GRACE`（0.25秒）の設計がそのまま効く。

**スワイプ（一回きりの**イベント**）ではこれが成り立たない。** 分岐は 0.19〜0.38秒
ごとに来る（40マップ・73,778サンプルの実測。49%は 0.19秒後）のに対しスワイプ1回は
150〜250ms かかるので、予約の寿命を別途延ばす必要があり、それでも取りこぼす。

### 原点は指に追従させること（トレーリング）

原点を最初に触れた点に固定すると、一方向へ倒したときのズレが残り続け、**直角へ
変えるのに指を90px動かす必要があった**。原点を指から半径 `JOY_R` 以内へ引きずると
30px で変わる（実測。3分の1）。

### 斜めでばたつかせないこと

素朴に `|dx|>|dy|` で4方向へ量子化すると、45度付近で毎フレーム左右に切り替わる。
別の軸へ乗り換えるには `JOY_HYST` 倍の優勢を要求する。実測では 1.0 で23回/秒
ばたつき、1.18 以上で 0 回。

### `wantFresh` は向きを変えた瞬間だけ立てること

毎フレーム立てると後退（Uターン）の門が開きっぱなしになり、以前直した
「勝手なUターン」が戻ってくる。

## 音

### BGMは必ずオリジナルで書くこと

ラリーXの原曲はナムコの著作物。**作風だけ寄せた自前のループ**を鳴らしている
（`BGM_LEAD` / `BGM_BASS`。8分音符32ステップ＝4小節、数字は MIDI ノート番号で
0は休符）。原曲の旋律を打ち込み直して使ってはいけない。

### AudioContext は必ずユーザー操作の中で解除する

iOS Safari は `AudioContext` を `suspended` で作る。ユーザー操作のハンドラの中で
`resume()` しないと一切鳴らない。最初の `pointerdown` と `keydown` で
`unlockAudio()` を呼んでいる。**ページ読み込み時に作ってはいけない**
（作っても suspended のままで、あとから resume しても鳴らない端末がある）。

### 先読みしてスケジュールすること

`setInterval` の中で「いま鳴らす」方式だとタイマーの揺れがそのまま
リズムの揺れになる。25ms ごとに起き、`actx.currentTime + 0.12秒` までに
入るぶんを **先に予約** している（`bgmTick()`）。

### 矩形波は頭と尻に傾斜をつける

ゲインを立ち上げ・切り下げなしで 0 から出すとプチッと鳴る。
`bgmVoice()` で 8ms の立ち上がりと短い減衰を入れてある。

### ミュートはマスターゲインで行う

スケジュールは止めずに `master.gain` を 0 にする。止めてしまうと解除した
ときにループの位相がずれる。状態は `localStorage` に残す。

燃料が 25 を切ると 8分音符が `STEP_BASE`(0.132秒) から `STEP_FAST`(0.098秒)
へ詰まり、テンポが上がる。

## 壁に突き当たったときの挙動

行き先は地形で決まる。どのケースでも車は止まらない。

| 地形 | 挙動 |
| --- | --- |
| L字路 | 開いている一方へ曲がって先へ進む |
| T字路 | 左右とも開くので既定は**右折**。ただしキー操作をしていればそちらが優先 |
| 袋小路 | 左右とも壁。戻るしかないので**反転** |

キー操作が優先されるのは、予約(`want`)の適用が壁判定より先に走るため。

### 予約(want)の寿命

**キーを押している間だけ予約が生きる。離すと `WANT_GRACE`(0.25秒)で消える。**
消えた状態は `want === null` で表す。

これが無いと「何も押していないのに勝手に曲がる」が起きる。予約が永久に残ると、
一度押した向きが開いているマスに来るたびに曲がり続けてしまう（実測で、→を
1回押して離しただけで20秒間に7回、無入力のまま勝手に曲がった）。

**`want` を `dir` と同じ値にする方式では消したことにならない。** その直後に車が
自動で曲がると `want` と `dir` がズレ、予約として復活する。必ず `null` にする。

後退(Uターン)だけは `wantFresh`、つまり「押したばかり」でないと通さない。
ここで**オートリピートを新しい押下に数えないこと**（`e.repeat` を除外する）。
数えてしまうと、長押し中に自動で2回曲がって向きが真逆になったとき、来た道は
かならず開いているのでUターンが通り、勝手に引き返す。

押したままタブを切り替えると `keyup` が来ないので、`blur` でも保持を解除する。

## 画面の向き

**ゲームは横持ち専用。** 縦持ちのスマホではタイトルと遊び方を出し、横向きを促す。

横持ちレイアウトは**高さ基準**で組んであること。幅基準だと iPhone 横持ちで
133px はみ出す。横持ちは「幅が余って高さが足りない」ので、`#stage` の高さを
`100svh` から決める。

### ステージの大きさは1本の式で決まる

```
height = min(100svh - 34px, 420px, (100vw - 予約) / アスペクト)
```

**アスペクト比・左右の予約幅・右列の中身はすべてこの1本の式に入る**ので、どれか
1つだけ変えると別の端末で破綻する。変えるときは iPhone SE (667×375) と
iPhone 15 (852×393) の**両方で測ること**。SE は横幅が制約、15以降は高さが制約に
なり、**効く変数が逆になる**のが罠。

広げすぎると逆に狭くなる。4:3 では最近の端末で横幅が余っていた（iPhone 15 で
53px）。十字キーがあるうちは 3:2 が上限だったが、廃した今は **16:10** が上限で、
それを超えると横幅の頭打ちが効いて面積が減る。

### オーバーレイは説明文だけを縮ませること（START が押せなくなる）

`#stage` は `overflow:hidden`。`#ov` の中身がステージの背より高くなると、
`justify-content:center` のせいで**上下が同じだけはみ出し、下端が切り落とされる**。
いちばん下にあるのは START / RETRY ボタンなので、**ボタンだけが消えて
「押せない・始まらない」**になる。見えないので原因も分かりにくい。

実際に踏んだ。説明文が10行まで育った時点で必要な高さは 308px。ステージは
iPhone SE 横で 329px しかなく、残り 18px。アーティファクトのように上下に
枠が付く環境ではそれだけで足りなくなり、ボタンが枠外へ出ていた。

| ステージの高さ | 修正前 | 修正後 |
| --- | --- | --- |
| 329px | ボタン下端が 1px はみ出し | 40px 余裕 |
| 297px | 15px はみ出し | 24px 余裕 |
| 277px | 25px はみ出し（当たり判定がフッターに） | 19px 余裕 |
| 201px | ― | 19px 余裕 |

直し方は**縮んでよいものを1つだけ決める**こと。

```css
#ov h2{flex:0 0 auto;}                      /* 見出しは縮ませない */
#ov p {flex:0 1 auto;min-height:0;overflow-y:auto;}  /* ここだけ縮む */
#btn  {flex:0 0 auto;}                      /* ボタンは死守 */
```

`min-height:0` が要る。**flex アイテムは既定で中身より小さくならない**ので、
これが無いと `overflow-y:auto` を付けても縮まずにはみ出す。

説明文も 10行 → 8行 に削った。ルールが増えるたびに1行足していたが、
スタート画面はステージの高さという上限を持っている。**1行足すときは
1行削る**こと。

### 右列の幅は「使える高さ」でも頭打ちにすること

右列の中身の背は**列の幅で決まる**。立ち絵は 4:3 なので 0.75W、レーダーは
33:25 なので 0.758W、ボタン列 54px、隙間 16px。合わせて **1.51W + 70px**。

だから `max-width:172px` で固定すると 330px の背が要ることになる。`#play` は
`100svh - 26px` しかないので、背の低い画面では右列が下へあふれ、**画面下の
注意書きや SMOKE ボタンと重なる**。実測:

| 画面 | #play の高さ | 右列の中身 | |
| --- | --- | --- | --- |
| 852×393 | 367px | 330px | 収まる |
| 852×349 | 323px | 330px | **7px あふれ** |
| 852×309 | 283px | 330px | **47px あふれ** |

使える高さからも幅の上限を決める。

```css
#side{max-width:min(172px, calc((100svh - 102px) / 1.51));}
```

102 = 26（注意書きの行）+ 70（中身の固定分）+ 6（安全代）。
`@supports not (height:100svh)` の保険側にも同じ式を置くこと。

**立ち絵やレーダーの縦横比を変えたら 1.51 も直すこと。**

### 画面の隅に固定で置くものと注意書き

注意書き（非公式表記）はガイドライン対応なので必ず読める場所に要る。画面の隅に
`position:fixed` で置くもの（確認用ビルドの⚙など）と場所を取り合うので、横持ちでは
`.site-footer{padding-inline:86px}` で左右を空け、残りの幅の中央に置いている。
文字そのものの矩形（`Range.getBoundingClientRect()`）で重なりを測ること ―
ブロックの箱は画面幅いっぱいなので、箱どうしで測ると常に「重なっている」と出る。

### 右列は「ステージが使えなかった余り」だけを吸う

`#stage{flex:0 0 auto}` / `#side{flex:1 1 auto; max-width:172px}`。ステージは
縮まない側なので、横幅が制約になる端末（iPhone SE）では右列が最小幅で止まり、
ステージは削られない。172px の上限は縦から決めた（立ち絵 0.75W ＋ レーダー
0.76W ＋ ボタン ＋ 隙間 が画面高に収まる上限）。

| 端末 | ステージ | 右列 | レーダー |
| --- | --- | --- | --- |
| iPhone SE (667×375) | 527×329 | 120px | 7.0px/マス |
| iPhone 13/14/15 (852×393) | 574×359 | 172px | 10.2px/マス |
| iPhone 15 Pro Max (932×430) | 634×396 | 172px | 10.2px/マス |

縦持ちの判定を**イベント任せにしないこと**。iOS Safari の `orientationchange` は
ビューポート（＝メディアクエリ）の更新より先に発火することがあり、その時点の古い値で
固定すると横向きに戻しても再評価されず、遊べないまま固まる。イベントに加えて
250ms 間隔でも再評価している。

## 配色

咲耶カラーのピンクを基調にする。ただし**危険色（敵車・燃料警告）は橙赤 `#FF4D2E`
へ逃がすこと**。ピンクのまま赤を使うと、自機のマゼンタ・CNPの紫〜桃のhue
（トワ262 / エマ292 / マカミ322 / タルト352）と混ざって「危険」が読めなくなる。
咲耶スクランブルも `magenta #FF2D9B` と `danger #FF4D2E` を別に持っている。

自機は**漆黒の車体＋マゼンタのリムライト**。ピンクを自機だけの徴にしてある。

壁の色を変えるときは、**11体すべてが背景から見分けられるかを確認すること。**
明るい紫（`#6b5588`）にしたときはトワのコントラスト比が 1.43 まで落ちた。
現在の `#5f3a5f` では全11体が比 2.0 以上ある（最悪はトワの 2.08）。

## 描画まわりのメモ

- **自機は ⌐◨-◨ カー**。`drawNoggles()` は咲耶スクランブルの同名関数と同じ作り。
  車体は進行方向に回すが、**ノグルズは回さない**（真上から見た車が曲がっても
  ⌐◨-◨ の顔が常に読めるようにするため）
- **名札**は幅を名前の実測に合わせてある。固定幅だと `TILE=24` より広がり、
  隣のマスのキャラの名札と重なって両方読めなくなる。それでもぶつかる場合は
  先に置いた名札を避けて逃がす。頭上に出すと HUD 帯（`y<22`）に潜る位置の
  ときは、最初から足元側に出して下へ逃がす
- キャラは暗い路面に沈むので、`hue` のオーラを下に敷いている
- **ロスターの未収集枠に「?」の仮絵を出さないこと。** あれは素材未配置を知らせる
  開発用の絵で、「まだ取っていない」の意味に流用すると**11枠が全部同じ顔**になり、
  あと誰が残っているのか読めなくなる。実際の絵から作ったシルエット
  （`silhouette()`）を出す。これは咲耶スクランブルの `drawRescueRoster()` が
  同じ失敗を踏んで得た教訓
- **ロスターは canvas の中の HUD 帯に置く。** ステージの外に帯を作ると
  レイアウトの高さを食い、ステージ全体が縮んでタイルまで小さくなる
  （実測で iPhone 15 が −16%）。canvas 内なら寸法は変わらず、犠牲になるのは
  見える迷路の縦 11.5% だけで済む
- **HUD帯の下に迷路を描かないこと。** 半透明の帯を重ねるだけでは迷路もCNPも
  名札も透けてロスターと混ざる。さらにカメラは自機を中央に置くので、迷路の
  最上段では自機が y=36 に来て **44pxの帯の真下に隠れる**。
  描画領域そのものを `VIEW_H = VH - HUD_H` に下げ、`clip()` で切り落とし、
  カメラも `VIEW_H` 基準にする。帯は不透明でよい（下に何も無いので）
- **自機を動かしたら直後にカメラも合わせること（`syncCam()`）。**
  `crash()` は `update()` を途中で `return` するので、ここを呼ばないと
  復活した最初の1フレームだけ古いカメラで描かれ、自機が画面外へ飛ぶ
- 名札の逃がし判定の基準は**描画領域の上端(0)**。世界は帯の下へずらして
  描くので、帯の高さを足してはいけない
- **タイヤ痕は塗りつぶさない。** `paint` は1マスにつき bit1=横に通った /
  bit2=縦に通った を持ち、通った向きに沿った2本の線で描く。方向を持たないと
  ただの塗り絵になり、走った軌跡が読めない
- **レーダーはコース画面の外（右列）に置く。** 画面内に重ねていたときは自機が
  レーダーの下に潜り、40回中6回（7回に1回）はCNPが見えないまま取りに行っていた。
  外に出すと重なりが起きないので、移動やフェードの処理そのものが要らない
- レーダーのCNPは **3×3px＋白フチで、11体とも同じ位相で点滅**させる。2×2の単色
  ドットでは11体の色が読めない。位相をバラすとチカチカして逆に読めなくなる
- レーダー用 canvas は**実寸×DPRで持つこと**。CSS幅が端末で変わるので、固定の
  内部解像度だとドットが潰れる。`height:auto` の明示も要る（`canvas{height:100%}`
  を受けると `aspect-ratio` が無視されて縦に伸びる）

## 迷路生成で守ること

**岩（`genMaze()` の値 `2`）は通路を塞ぐので、置く場所によっては迷路が分断される。**
分断されると自機からCNPへ到達できず、クリア不可能な盤面になる。

置く前に `countReachable()` で「その1マスぶんしか通路が減らないか」を確かめ、
分断するなら置き直すこと。この判定が無いと、実測で

| | 発生率 |
| --- | --- |
| 1体以上が到達不能（クリア不可能） | 6〜7% |
| 全11体が到達不能（完全に詰み） | 1.5〜1.8% |

つまり**16回に1回はクリアできない迷路**が出る。判定を入れても岩は8個すべて置けて
いて、`newGame()` の所要は 0.5ms。盤面は1プレイに1回しか作らないので、素朴な
探索で十分足りる。

迷路本体（掘削と、その後に壁を26%開ける処理）は分断を作らない。掘削は全体が
つながった完全迷路を作り、壁を開ける処理は通路を増やすだけだから。**分断する
可能性があるのは岩だけ。**

## ポーズ（画面中央のボタン）

コースの中央に半透明のボタンを置き、押すと止まる。止めている間も**描画は続け、
`update()` だけ止める**（`loop()` の `if(!orientationBlocked && !paused)`）。
PC は P と Esc でも切り替わる。姉妹作（咲耶スクランブル）と同じ作りにしてある。

### スティックと食い合わせないこと

この作品の操作は**画面のどこでも触れた場所にスティックが出る**浮動式。中央の
ボタンを普通に押せるようにすると、**画面の真ん中に死角ができて曲がれなくなる**。

そこでボタンはプレイ中 `pointer-events:none` にして指を canvas まで通し、
ポーズは canvas 側で拾う:

- 押し始めが中央の円の中で、かつ
- スティックが向きを出しておらず（`!joy.dir`）、かつ
- 指の移動が `JOY_DEAD` 未満、かつ
- 500ms 未満で離した

このときだけポーズにする。**止めている間だけ** `pointer-events:auto` に変え、
再開はボタンを押させる（このとき canvas 側は `paused` で早期 return するので、
スティックは出ない）。

### 止めるときは入力を捨てること

押したまま止めて離すと `pointerup` が飛ばないことがあり、再開した瞬間その向きへ
走り出す。`setPaused(true)` で `heldDir` / `heldCode` / `emitting` とスティックを
必ず捨てる。

### 再開時は `last` を今に合わせること

`last` を放置すると、止めていた時間がまとめて `dt` に乗る。`dt` は 0.05 で
頭打ちにしてあるので壁は抜けないが、1フレームぶん余計に進む。

### 幕の点滅に `t` を使わないこと

`t` は `update()` の中で進むので、**止めている間は止まっている**。点滅は
`performance.now()` で数えること。

### `#ov` の z-index

`#pause` は `z-index:6` を持つ。`#ov`（スタート/リザルトの幕）に z-index が
無いと、DOM順では後ろでもポーズボタンが幕の上に出る。`#ov{z-index:8}`。

## ワープトンネル（F4）

外周の左右に口を1組あけ、片方へ走り込むともう片方から出る。

### 地続きに繋がないこと（瞬間移動方式）

左端と右端を「continuous な世界」として繋ぐと、`isWall()` の
**「盤外は壁」という前提が崩れる**。そこが崩れると

- `canGo()` / `stepCar()` の壁判定
- `aiThink()` の候補列挙
- `farthestCell()` と `countReachable()` の幅優先探索
- カメラのクランプ（`syncCam()`）

が全部書き換えになる。そこで**口の中心に着いた瞬間に座標ごと置き換える**方式に
した。盤面の形も判定も何ひとつ変わらない。

### 口は `grid` の値 `3`。壁ではないが「通路」でもない

`isWall()` だけが `3` を通す。`openCells()` は外周（`1..COLS-2`, `1..ROWS-2`）を
見ないので、**CNP・敵の湧き位置・出口が口の上に来ることは構造的にありえない**。
出口はこれとは別に `farthestCell()` が `0` のマスだけを歩くので二重に安全。
300回生成して口と出口が重なった回数は 0。

### 塗りは口の上で加点しないこと

踏破率の分母は `openCells().length`（＝外周を含まない）。口の上を数えると
**100%を超える**。`update()` の塗り処理に `grid[cy][cx]===0` を足してある。

### ワープ判定は `stepCar()` の `atCenter` ブロックの先頭に置くこと

口の外側は壁なので、先に予約の適用や「壁に当たったら右折」の自動旋回が走ると、
**外を向いたまま曲げられて二度と抜けられない**。どの分岐よりも前に置くこと。

飛ばした直後は 1マスぶん(`step`)進めてから `return` する。中心に置いたままだと
次のフレームもその口の中心判定に入る。向き（`out`）の条件で二重ワープはしないが、
1フレーム止まって見える。

### 口の内側が必ず通路であること

迷路は奇数マスを掘るので `x=1` と `x=COLS-2` は必ず通路。岩も `x>=2` にしか
置かない。だから**奇数行を選べば口の内側は必ず開いている**（300回生成して詰まり 0）。
`y=1` はスタート行なので除く ― 走り出した瞬間にワープできてしまう。

### 敵も通れるが、抜けた先でしばらく遅い

`TUNNEL_SLOW`(0.55) × `TUNNEL_TIME`(1.4秒)。本家パックマンと同じ扱いで、
**トンネルは追われている側の武器**になる。減速は `e.speed` を書き換えて効かせる
こと ― `stepCar()` は `atCenter()` のしきい値にも `c.speed*k` を使うので、
速度を通さずに移動量だけ落とすと壁をすり抜ける（燃料切れの減速と同じ罠）。

### 効き目（200回生成して実測）

| | マス |
| --- | --- |
| スタート→出口の最短距離（トンネル無） | 60.2 |
| 同（トンネル有） | 40.0 |
| 平均の短縮 | 20.1（33%） |
| 短縮ゼロだった迷路 | 22/200 |

**33%の近道**なので、難易度への影響は小さくない。緩すぎるなら口を狭める
（`digTunnels()` の行を端に寄せる）か、自機も抜けた直後は遅くする。

## 調整しやすい定数

```js
const TILE=24, COLS=33, ROWS=25;   // 迷路の寸法
const CHAR_SIZE=22;                // キャラの描画サイズ(px四方)
const CHAR_HIT=14;                 // 回収の当たり判定
```

敵は4台（`placeEnemies()`）、岩は8個（`genMaze()`）、燃料は基本 1.3/秒 + 煙を
出している間 3.2/秒（`update()`）。

塗りとゴールは `PAINT_PTS`（1マス5点）と `GOAL_BONUS`（800点）。

BGMは `BGM_LEAD` / `BGM_BASS`（8分音符32ステップ）と
`STEP_BASE` / `STEP_FAST`（8分音符の長さ）。

ワープトンネルは `TUNNEL_SLOW`（敵の減速率 0.55）と `TUNNEL_TIME`（1.4秒）。

ロスターは `ROSTER`（`slot` 20px / `gap` 3px / `y` 24px / `flash` 0.75秒）。
`HUD_H` は `ROSTER.y + ROSTER.slot` = 44px で、HUD帯の高さと名札の逃がし判定の
両方に使う。11枠 × 20px + 隙間 3px = 250px が canvas 614px の中央に収まる。
姉妹作は canvas 960×540 に 36px 枠なので、同じ比率まで落とした値。

スティックは `JOY_DEAD`（12px・無入力の範囲）、`JOY_R`（24px・原点が指を追う
半径）、`JOY_HYST`（1.20・軸を乗り換える優勢比）。

画面は `#stage` の `aspect-ratio:8/5` と canvas の `width=614 height=384`（16:10）。
**両方を揃えること。**

残機は `LIVES_START`（3台）、復活後の無敵は `INVUL`（2秒）。

速度は定数にまとめてある。単位は **60fps 換算の px/フレーム**。

```js
const SPD_PLAYER = 2.625;   // 2.1  * 1.25  実速度 約158px/秒
const SPD_ENEMY  = 2.1875;  // 1.75 * 1.25
const SPD_DRY    = 1.75;    // 1.4  * 1.25  燃料切れ後。敵より遅い
```

1.25 倍は実機で決めた値。**自機と敵の比 1.20 は変えていない**（変えると敵の
脅威度が別物になる）。燃料切れ後の 1.75 も同じ比率で下げてあり、敵
（2.1875）より遅いので必ず追いつかれる。

### 速度はフレームレートに依存させないこと

`stepCar()` と `aiThink()` は、60fps を 1 とするフレーム倍率 `k = dt*60` を
受け取り、`step = speed * k` だけ進む。これを怠って毎フレーム固定量だけ進める
と、**120Hz の端末で2倍速**になる（燃料だけは秒単位で減るため、実質的に難易度
が別物になる）。iPhone / iPad の Pro 系は 120Hz なので実害が出る。

`atCenter()` の**しきい値は必ず `step` と同じ値**にすること。ここがズレると、
重いフレームで中心を飛び越えたのに気づけず、曲がり損ねて壁をすり抜ける。
`dt` は `loop()` で 0.05 秒に制限してあるので `k` は最大 3、1フレームの移動量
は最大 7.9px（2.625*3）で TILE=24 を飛び越すことはない。**速度を上げるときは
この余裕を必ず確かめること**（TILE の半分を超えると壁を抜ける危険がある）。

### `newGame()` をプレイ中に呼ばないこと（`rafId`）

`newGame()` は `requestAnimationFrame(loop)` でループを立ち上げる。プレイ中に
もう一度呼ぶと**二本目のループが走り、`update()` が毎フレーム2回**呼ばれる＝
まるごと2倍速になる。RETRY ボタンはオーバーレイごと隠れているので実機では
押せないが、`rafId` を持って `cancelAnimationFrame()` してから張り直している。

テスト用フックから `__new()` を連打して実際に踏んだ。1フレームに2回 `update()`
が走ると、2回目は `dt` がほぼ 0 になって自機が動かない。「停止フレーム」を
数えていた計測が 11.8% も誤検知したのはこれが原因で、**ゲーム側のバグではなく
計測側の呼び方の問題**だった。同じ数え方をするときは注意。

### 燃料切れの減速は `stepCar()` より前に効かせること

`player.speed` は `update()` の先頭で `fuel>0 ? SPD_PLAYER : SPD_DRY` に
切り替えている。`stepCar()` の後で変えると、`atCenter()` がその
フレームだけ古い速度のしきい値で判定することになり、中心の判定を取りこぼす。

### F14 — 岩を本家ラリーXの挙動にする

同じ**。見た目が茶色いだけで、当たることすらできない（壁と同じ自動旋回が働く）。

本家ラリーX（1980・ナムコ）の岩は**壁ではなく、通路に置かれた危険物**だった。

| | 本家 | いまのラリー |
| --- | --- | --- |
| 自機が岩に当たる | **即ミス。残機が1つ減る** | 当たれない（壁として曲がる） |
| 敵が岩に当たる | **スピンする**（煙幕・敵同士の衝突と同じ） | 当たれない |
| 岩の数 | 面が進むと増える | 常に8個 |

変えること

- `isWall()` から `2` を外す。通れる地形にして、突っ込めるようにする
- 自機が乗ったら `crash()`（敵に当たったときと同じ）。`invul` 中は無効
- 敵が乗ったら `e.spin`（煙幕と同じ機構を再利用する）

**副産物として `countReachable()` の連結保証が不要になる。** 岩が通路を塞がなく
なるので、「岩が迷路を分断してクリア不能になる（実測 6〜7%）」という後述の罠が
根本から消える。**この判定を消すのを忘れないこと。**

着手前に測ること

- **1プレイあたり何回岩に乗るか**（ボットで実測）。8個が多いのか少ないのかを
  誰も知らないまま数を決めないこと
- **避けられない配置が出ないか**。曲がった先が岩、など。理不尽な即死が混ざるなら
  数ではなく置き方の問題

読みどおり、拡大できるページでは Safari がタップのたびにダブルタップ/ピンチの判定を
走らせ、ポインタの列が素直に来ないせいで `joyEnd()` の4条件が崩れていた。

**しきい値（12px / 500ms / 半径32px）は変えていない。** 最初の記録では「しきい値が
厳しすぎる」を第一の容疑に挙げていたが、それは誤りだった。緩めていたら、直らないまま
判定だけ雑になっていた。**原因を掴む前に対症療法へ走らないこと。**

以下は当時の記録（同じ罠を踏んだときの手がかりとして残す）。

#### （記録）B1 の切り分け

コースの中央をタップしてもポーズにならない。

**切り分けの決め手:** 同じ端末・同じ指で、

| | ポーズ |
| --- | --- |
| アーティファクト（**iframe の中**） | **効く** |
| 公開版 GitHub Pages（**トップレベルのページ**） | **効かない** |

`build12.py` はポーズにもポインタ処理にもビューポートにも触っていない（唯一の
touch 系の変更は `padding-inline` の追加だけ）。**ゲームのコードは両者で同一**なので、
違うのは環境だけ。

**そしてB2（勝手に拡大する）も公開版だけで起きている。** これが効いていると見る。

iOS Safari はトップレベルのページで `user-scalable=no` を無視するので、**公開版の
ページは拡大できる状態**にある。拡大できるページでは、Safari はタップのたびに
ダブルタップ/ピンチの判定を走らせる。その間ポインタの列が素直に来ない
（`pointerup` の代わりに `pointercancel` が飛ぶ、座標がずれる、ダブルタップの
待ち時間ぶん遅れる）。`joyEnd()` のタップ判定は

```js
const tap = !!joy && joy.onPause && !joy.dir
  && Math.hypot(e.clientX-joy.sx, e.clientY-joy.sy) < JOY_DEAD   // 12px 未満
  && performance.now()-joy.t0 < 500;                             // 500ms 未満
```

の4条件すべてを要求するので、どれが崩れても成立しない。**iframe の中では
ピンチ操作の主導権が親ページ側にあるため、この妨害が起きない** ― アーティファクトで
効くのはそのためだと考えている。

**手順を守ること。**

1. **先に B2 を直す**（ジェスチャの打ち消しを入れる）
2. **そのうえで B1 を実機で再確認する**
3. **それでも効かないときに初めて**、実機で指の移動量と押下時間を測り、
   しきい値（12px / 500ms / 半径32px）を見直す

**しきい値から先に触らないこと。** 原因がジェスチャ側なら、緩めても直らないまま
判定だけ雑になる。最初にこの記録を書いたときは「しきい値が厳しすぎる」を第一に
挙げていたが、**アーティファクトでは効くという情報で否定された。**

なお「押しても何の反応も返らない」のは別途改善の余地がある。プレイ中のボタンは
`pointer-events:none` なので `:active` も出ず、当たったのか外したのかが分からない。

**再現環境の注意:** headless Chromium ではこの不具合は出ない。**iOS Safari の
トップレベルのページでしか起きない。** 手元のテストが通っていたのはそのため。

#### B2 画面が勝手に拡大する（対処済み・実機での確認待ち）

タップして操作していると画面がズームすることがある。

**`user-scalable=no` は iOS Safari では効かない**（iOS 10 以降、意図的に無視される）。
ラリーはビューポートの指定しか持っておらず、**ズームを打ち消すコードが1つも無かった**
（`gesturestart` / `gesturechange` / `touchmove` のハンドラが 0 件）。

**iOS のピンチズームは `touch-action:none` では止まらない。** WebKit独自の
`gesture*` イベント経由で起きるので、明示的に打ち消す必要がある。姉妹作から移植した。

```js
const zoomLock = () => state==='play';
for(const type of ['gesturestart','gesturechange','gestureend']){
  document.addEventListener(type, e=>{ if(zoomLock()) e.preventDefault(); });
}
// gesture* を持たないブラウザ向けの保険。2本指の動きそのものを打ち消す。
// passive:false を明示しないと preventDefault が無視される
document.addEventListener('touchmove', e=>{
  if(zoomLock() && e.touches.length>1) e.preventDefault();
}, {passive:false});
```

**打ち消すのは走っている間だけにすること。** スタート画面とリザルトには文字が多い
ので、拡大して読みたい人のためにズームできるままにしておく（姉妹作と同じ方針）。

**ポーズ中も走行中と同じ扱いにすること。** ここでズームを許すと、拡大したまま
再開されて元の木阿弥になる。

**1本指の `touchmove` は絶対に打ち消さないこと。** スティックがそれで動いている。

**ビューポートの指定は変えていない。** `maximum-scale=1,user-scalable=no` は iOS では
無視されるので消しても iOS の挙動は変わらないが、Android では効いているため、
消すとそちらのズーム可否が変わる。手元で確認できない変更なので触らなかった。

**確認方法の限界:** `gesture*` は WebKit 独自で、**Chromium は発火しない**。手元では
イベントを自分で `dispatchEvent` して「自分のリスナーが打ち消すか」までしか確かめ
られない。**実際にピンチが止まるかは実機でしか分からない。**

#### B4 アプリ化すると画面に収まらない（原因特定・対処済み）

## 高さの当てにならない箱の中で中央寄せをしない（iOSのホーム画面起動）

**嘘をついていたのは `100svh` ではなく `html,body{height:100%}` だった。**

決め手になった実機の計測（横と縦を続けて取ったもの）。

```
横 NG はみ出し 右0 下26 左0 上-52 / 画面750x390 svh390 vh390px 外844x390
                                   可視750x390@1.00 cl750x390 dpr3 / アプリ1
縦 OK 収まっている 右-8 下-61 左-8 上-47 / 画面390x797 svh797 vh797px 外390x844
                                   可視390x797@1.00 cl390x797 dpr3 / アプリ1
```

**CSS が見ている高さは全部正しい。**

| | |
| --- | --- |
| `画面`(innerHeight) / `svh` / `--vh` / `cl` | **390 で全部一致** |
| `可視…@1.00` | **拡大していない** |

にもかかわらず `#play` が **上52px の位置から始まって、下に26px あふれていた**。
`#play` 自身の高さは `390 - 26 = 364` で**式どおり**なので、**ずれているのは
「どこから始まるか」だけ**。

### 原因 ― `height:100%` が返す箱が実際より大きい

`body` は `display:flex; align-items:center` で中身を**縦中央に置いている**。
箱の高さが実際より大きければ、その差の**半分だけ中身が下へずれる**。

逆算したら一意に決まった（手元で `body` の高さだけ変えて再現）。

| `body` の高さ | `#play` の上 | はみ出し下 |
| --- | --- | --- |
| 390（正しい） | 5 | -21（収まる） |
| **484** | **52** | **26** ← **実機の報告と完全一致** |
| 500 | 60 | 34 |

そして **484 = 390 + 94**、**94 = 外844 − 画面750**。
横持ちのノッチの左右インセット（47×2）が、なぜか**高さ側に混ざって**いた。

**`svh` は無実だった。** `#17` で `--vh` を足したのは原因の読み違いで、
症状が変わらなかったのはそのため。`--vh` 自体は害が無いので残してある。

### 直し方 ― 中央寄せをやめて上端に固定する

```css
@media (orientation:landscape) and (max-height:600px) and (hover:none){
  body{align-items:flex-start;}   /* 箱の高さが嘘でも、上端は必ず0 */
}
```

**箱の高さを当てにしない。** 高さの嘘は「中央寄せ」を通してはじめて位置のズレに
化けるので、中央寄せをやめれば嘘があっても影響しない。

手元で `body` の高さを 484 / 500 / 600 / 750 と嘘の値に差し替えても、
**どれも `上0` で 26px 余らせて収まる**ことを確認した。

**教訓: 画面いっぱいに組むレイアウトで `align-items:center` を使わない。**
`height:100%` も `100svh` も端末によっては嘘をつくが、**上端に貼り付けてあれば
嘘の影響は「下に余る／足りない」だけで済み、中身が画面の外へ押し出されない。**

### まだ残っている分（B4の続き・原因未確定）

中央寄せを直したら**症状は軽くなったが、下が 21px 切れたまま**という報告が来た。
スクリーンショットから実寸を測った結果（画面 844x390・dpr3）。

| | |
| --- | --- |
| 中身の左端 / 右端 | **57 / 797** ―― 左右に **47px ずつ**の余白 |
| 中身の上端 | **47** |
| SMOKE の枠の上端 | **357**、最低の高さ 54 を足すと **411** |
| 画面の高さ | **390** → **21px あふれている** |

左右の 47 はノッチの逃げ（`外844 − 画面750 = 94 = 47×2`）なので説明がつく。
**問題は上の 47。** ここで候補が2つあり、**どちらも数字が合ってしまう**。

| 候補 | 中身 | 上が47になる理由 |
| --- | --- | --- |
| A | **古いビルドを見ている** | 中央寄せのまま。`body` の高さが 474 なら 上47 |
| B | **ビューポート自体が下へずれている** | セーフエリアが位置にだけ効き、高さには効いていない |

**A と B では直し方が正反対**（A は何もしなくてよい、B は `viewport-fit=cover` を
入れて `env(safe-area-inset-*)` を自分で引く）。**推測で片方を実装しない。**

見分けるために、計測の帯に2つ足した。

```
… dpr3 逃げ0/0/0/0 / 版2026-09-18 05:24 / 横1 …
```

| 読み方 | |
| --- | --- |
| `版` が古い | **A**。キャッシュを見ているだけ |
| `版` が最新 かつ `上0` と出るのに画面では切れている | **B**。帯はビューポート基準なので、ビューポートごとずれていると気づけない |
| `逃げ` が `0/0/0/0` でない | `viewport-fit` 未指定なのに逃げが出ている＝**B の裏付け** |

**教訓: 計測の出力には必ず「どのビルドか」を入れること。** #18 でそう書いたのに
スタート画面にしか出しておらず、帯だけ送られてきたときに判別できなかった。

### （参考）最初に取った計測と、その読み違い

```
LAYOUT はみ出し 右0 下26 左0 上-5 / 画面750x343 svh390 dpr3
```

ここでは `画面343` と `svh390` が食い違っていたので **`svh` が嘘をついている**と
読んだ。だが後日の計測では `画面390 svh390` で一致しており、**食い違いは常時では
なかった**（回転直後など、一時的に古い値が返る場面があるとみられる）。

**はみ出し `下26` が両方で同じだったのに、原因は別だった。**
同じ数字が出ても同じ原因とは限らない ―― `26` は式の `- 26px` に由来するので、
**どちらの壊れ方でも 26 になる**。数字の一致を根拠にしないこと。

### （不採用）実測と突き合わせる

JS で測った `innerHeight` を `--vh` に入れ、**両者の小さい方**を使う。

```css
#play{height:calc(min(100svh, var(--vh, 100svh)) - 26px);}
```

- `var()` の既定値を `100svh` にしてあるので、**JS が走る前も従来どおり動く**
- `min()` にしてあるので、`--vh` が大きすぎても `svh` で頭打ちになる
  （iOS Safari の URL バーが動く場面で、`svh` を選んだ意図を壊さない）
- `setVH()` は**本体より前**に置く。最初の描画からズレていない値で組ませるため
- 起動直後は値が落ち着かないので `100 / 300 / 600 / 1200 / 2500ms` で測り直す

**`100svh` を使う場所を増やすときは、必ずこの形にすること。** 素の `100svh` を
書くと、また同じ崩れ方をする。

### 計測（`?diag=1`）は消さないこと

この原因は**手元では一切再現しない**。headless Chromium では `svh` と
`innerHeight` が常に一致するので、嘘をつく状況そのものが作れない。
**実機に数字を言わせる以外に手が無かった。** 同じ種類の崩れがまた出たときのために、
計測は残してある。

#### （記録）B4 の切り分け

公開版をホーム画面に追加して起動すると、レイアウトが画面からはみ出す。
ブラウザで開いているときは収まっている。

**ラリーには「アプリとして起動されたとき」の対応が1つも入っていない。**
姉妹作（咲耶スクランブル）には全部入っている。

| | ラリー | 姉妹作 |
| --- | --- | --- |
| `apple-mobile-web-app-capable` | **無し** | あり |
| `apple-mobile-web-app-status-bar-style` | **無し** | `black-translucent` |
| `viewport-fit=cover` | **無し** | あり |
| `env(safe-area-inset-*)` | **0か所** | **6か所** |
| `apple-touch-icon` | あり | あり |

`apple-touch-icon` だけ流用してあるので**ホーム画面のアイコンは付く**が、
その先の対応が抜けている。

ビューポートの指定も姉妹作と違う。

```html
<!-- ラリー: maximum-scale と user-scalable は iOS で無視される。viewport-fit が無い -->
<meta name="viewport" content="width=device-width,initial-scale=1,maximum-scale=1,user-scalable=no">
<!-- 姉妹作 -->
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

**なぜはみ出すか。** 横持ちのレイアウトは `100svh` に貼り付けてある
（`#play{height:calc(100svh - 26px)}` / `#stage{height:min(calc(100svh - 34px), …)}`）。
ノッチ・ホームインジケータ・ステータスバーのぶんを引いていないので、
**ブラウザが返す高さと実際に使える高さがズレると、そのまま画面外へ出る。**
`status-bar-style: black-translucent` はステータスバーを内容の上に重ねる指定なので、
**safe-area の余白と必ずセットで入れること。** 片方だけ入れると内容がバーの下に潜る。

**B2（拡大）は原因ではない。** 「アプリ化した直後から、ピンチする前にはみ出す」
と確認が取れた。拡大の持ち越しではない。**B2 を待たずに着手してよい。**

**safe-area 不足という見立ては弱い。** ラリーは `viewport-fit=cover` を指定して
いないので、**iOS はすでにセーフエリア内にビューポートを収めている**。つまり
`env(safe-area-inset-*)` は全部 0 で、**引くものが無い**。余白を足しても何も変わらない。

**端末は iPhone と確認済み**（iPad なら `max-height:600px` が外れる説で説明できたが、
iPhone の横持ちは 393px なのでその条件は通る）。**つまり原因はまだ分かっていない。**

**決定的な証言:「何か触ったら画面が綺麗に収まることもある」。**
つまり**レイアウト自体は正しく収まれる**。起動直後だけ CSS が見ている画面サイズが
実際とズレていて、何かの拍子に再計算が走ると正しくなる、という形をしている。

**だから勘で直さず、実機に数字を言わせる。** 崩れている値だけでは足りない ―
**直った瞬間の値と並べて初めて、どちらが正しい画面サイズなのかが分かる。**

計測は1回きりにしないこと。起動直後に **0 / 100 / 300 / 600 / 1200 / 2500 / 5000ms**
で測り、`resize` `orientationchange` `pointerup`（＝「何か触った」）でも測り直して、
そのつど最新の値に書き換える。`最悪` に最大のはみ出し量を残すので、**直ったあとでも
「崩れていた」事実は読める。**

```
LAYOUT はみ出し 右R 下B 左L 上T / 画面WxH svhS dprD
       / 横1 高600以下1 hover0 fine0 アプリ1
```

| 読み方 | |
| --- | --- |
| `高600以下` が **0** | 横持ちのメディアクエリが外れている。**レイアウトの選択が間違っている** |
| `svh` が `画面` の高さより**大きい** | CSS が見ている高さと実際の表示領域がズレている |
| `アプリ` が **1** | スタンドアロン起動として認識されている |

**出すのは URL に `?diag=1` が付いているときだけ。保存はしない。**

以前は `localStorage` に残し、アプリ起動で崩れていたら自動でも出していた。意図は
「余計な手間なく数字を取る」だったが、**実際には逆になった。**

- 一度 `?diag=1` で開くと、消すのに `?diag=0` がもう一度要る
- **アプリと Safari で保存領域が別**なので、片方を消しても残る
- **プライベートウィンドウでは保存できず**、挙動が読めない

**調べるための道具が、調べる邪魔をしていた。** URLを閉じれば必ず消える形にした。

**確かめ方:** `https://naonao1971.github.io/SakuyaRallyCnp/?diag=1` を Safari で開き、
**その状態でホーム画面に追加する。** 設定は `localStorage` に残るので、アプリとして
起動しても効いたまま。`?diag=0` で解除。

**ホーム画面のアプリは古いファイルを強くキャッシュする。** 直したのに変わらないときは、
**一度削除してから追加し直すこと。**

### 実機の不具合を聞くときは「どこで見ているか」を先に確かめること

同じ症状でも、見ている場所で原因も対処も変わる。**先に聞かないと堂々巡りになる。**
実際になった。

| 見ている場所 | キャッシュ | localStorage | ホーム画面に追加 |
| --- | --- | --- | --- |
| ふつうの Safari | 効く | 残る | できる |
| **プライベートウィンドウ** | 効かない | 残らない | **できない（iOSの仕様）** |
| **ホーム画面のアプリ** | **強く効く** | **Safari とは別枠** | ― |

帯の末尾の `アプリ1` / `アプリ0` で、アプリから来たのかブラウザから来たのかは判別できる。

### 計測の出力には版が分かるものを入れること

「直したのに変わらない」と言われたとき、**古いビルドを見ているのか、直っていないのか**が
区別できずに往復した。今回は出力の形が変わっていた（`LAYOUT` → `NG`/`OK`、`vh` の有無）
おかげで偶然判別できたが、**偶然に頼っている。** 次に計測を触るときはコミットの
短縮ハッシュを出力に入れること。

**原因の候補は2つ。直し方がまったく違う。**

横持ちのレイアウトはこの条件でしか当たらない。

```css
@media (orientation:landscape) and (max-height:600px) and (hover:none){ … }
```

| 候補 | 中身 | 直し方 |
| --- | --- | --- |
| **(a) safe-area 不足** | 横持ちのレイアウトは当たっているが、ノッチ・ホームインジケータのぶんを引いていない | 上の4点を移植する |
| **(b) メディアクエリが当たっていない** | `max-height:600px` か `hover:none` が外れ、PC用（`#stage{width:614px}` 固定）か既定の縦積みが適用されている | **条件そのものを見直す。safe-area を足しても直らない** |

**(b) を先に潰すこと。** はみ出し方（ステージが画面に対して大きすぎ、SMOKEが
右下で切れている）は、横幅 614px 固定の**PC用レイアウトが当たっている**ときの
見え方に近い。safe-area の不足だけなら、ここまで大きくはならない。

確かめ方は、`matchMedia` の結果と `innerWidth/innerHeight` を
`#crash` の帯に出すだけでよい（帯は既にあるので数行で済む）。**勘で safe-area を
足して「直った気がする」で終わらせないこと。**

直し方は姉妹作の移植でよい。

```css
padding: 8px 8px calc(8px + env(safe-area-inset-bottom));
left:   calc(18px + env(safe-area-inset-left));
right:  calc(12px + env(safe-area-inset-right));
```

**再現環境の注意:** headless Chromium では再現しない。**iOS の
スタンドアロン起動でしか起きない。** 確認は実機でしかできない。

#### B5 iPad 横持ちで `#play` が画面からはみ出す

`?diag=1` の計測機構を作った副産物として見つかった（手元の 1133×744 で再現）。

```
LAYOUT はみ出し 右-286 下24 左-286 上33 / 画面1133x744 svh744 / 横1 高600以下0 hover0 fine0
```

**`高600以下` が 0**。横持ちのレイアウトは `max-height:600px` を要求するので、
iPad の横持ち（高さ 744px）では**外れて既定の縦積みが当たる**。縦積みは
ステージ 350px ＋ 右列 300px と背が高く、`#play` が 57px はみ出して
`overflow:hidden` で切られる。

B4 と**同じ種類**の不具合（レイアウトの選択が端末に合っていない）だが、
**B4 は iPhone で起きているので別物**。B5 の修正が B4 を直すとは限らない。

#### B3 アイコン（差し替え済み。OGPはドメイン待ち）

`favicon-32.png` と `apple-touch-icon.png` が**咲耶スクランブルのものとバイト単位で
同一**だった（流用したまま差し替え忘れ）。ホーム画面やブックマークに飛行機が出ていた。

**ラリーカーの絵に差し替えた。** 生成スクリプトは `tools/mkicon.py`。

```
python3 tools/mkicon.py apple-touch-icon.png favicon-32.png
```

- 枠と配色は姉妹作に揃える（暗い四角＋金の枠）。並べたときに姉妹作だと分かる
- **真上から見た形（ゲーム中の自機と同じ向き）は没にした。** 32px ではただの
  ピンクの塊にしか見えない。**横から見た形の方が、小さくても一目で車と分かる**
- 窓は暗い台形＋明るい四角2つ。⌐◨-◨ の気配を残してある
- スーパーサンプリング8倍→LANCZOS縮小。32px と 180px は**別々に描く**
  （32px を拡大すると潰れる）

**OGP はまだ入っていない。** `og:url` と `og:image` は絶対URLなので、**ドメインが
決まらないと書けない。** 画像は `assets/rally_title.jpg`（1200×674）がそのまま使える。

### F8 — ランキング登録（仕様は確定済み）

| | |
| --- | --- |
| 置き場所 | ラリー専用の新しいスプレッドシート＋新しいGASデプロイ（姉妹作と**共用しない**） |
| 列 | スコア／ニックネーム／X ID／登録日時／端末／**踏破率**／**回収CNP**／**クリア** |
| フォームを出す条件 | TOP10に入る点数のときだけ（姉妹作の `qualifiesForTop10()`） |
| X IDの確認 | `unavatar.io` のアバターが読めるか（姉妹作と同じ） |
| 不正対策 | サーバー側で **6,000点超を拒否**（理論上限は実測 5,555点 = CNP2,420＋塗り2,335＋ゴール800） |
| クリア後 | 2秒後にフォームへ自動スクロール |
| 画面 | **横持ちでも縦持ちでも**、ゲームの下に普通のページ要素として置く（姉妹作と同じ） |

**共用しないこと。** 同じGASを再デプロイすると、稼働中の咲耶スクランブルの
ランキングを巻き込んで壊す。スコアの桁も意味も別物なので混ぜる利点がない。

**縦持ち専用にしないこと。** `#rotate` は `isMobileDevice && portraitMQ.matches`
のときしか出ないので、**PCでは永久に表示されない**＝PCから登録できなくなる。

先に**ページをスクロールする形にする**改修が要る（`body{overflow:hidden}` を外し、
`touch-action:none` を `#play` へ移す）。1画面の中の計算式（ステージの高さ・
右列の幅）には手を入れない。**土台の改修と通信は別のPRに分けること。**
